# 我让 Codex 接管一台三星电视：从国区到港区的真实改造记录

家里有一台三星 QA65Q70RAJXXZ，属于 2019 年的 Q70R 系列。电视本身没有坏，面板也还不错，但国区 Smart Hub 的应用商店里没有 Netflix 和 YouTube。最省事的办法当然是买个盒子，可我更想知道：能不能不添设备，只靠现有的 Mac、路由器和一部安卓手机，把这台电视真正切到香港区？

这次我没有自己在论坛里来回拼教程，而是把任务直接交给了 Codex。它负责发现电视、生成遥控工具、分析网络连接、设计代理路径、判断错误原因、读取我拍下的工程菜单照片，并在每一个高风险步骤前收紧操作范围。我负责的事情很少：拿遥控器按确认键、在电视前拍照，以及最后用带红外的安卓手机发送两组按键。

最终，电视的地区代码从中国大陆切换到了香港，Smart Hub 出现了 Netflix、YouTube、Disney+、Prime Video、Spotify、Viu、Apple TV 和 Apple Music。YouTube 和 Netflix 都能正常使用。Apple TV 也完成了重装并能打开，但因为我当时登录的是中国大陆 Apple ID，仍然提示账号地区不受支持。这一点我放到后面详细说。

> 这是一篇真实操作记录，不是所有三星电视都通用的刷机教程。工程菜单中的错误操作可能导致电视无法开机、画面异常或失去保修。动手前必须拍下全部原值，只修改已经确认的地区字段。

## 第一步：让 Codex 在局域网里找到电视

电视和 Mac 在同一个局域网，但电视走有线、Mac 走 Wi-Fi。这并不影响两台设备通信，只要它们处在同一个网段，路由器没有开启客户端隔离即可。

Codex 先扫描局域网，确认电视的地址位于 `192.168.10.x`，并识别出三星电视的局域网控制服务：

- `8001` 端口可用于发现和普通 WebSocket 控制；
- `8002` 端口可用于加密 WebSocket 遥控配对；
- 第一次连接时，电视会弹出授权提示，需要我在屏幕上点击“允许”。

随后，Codex 在 Mac 上直接写了一个 Node.js 遥控脚本。脚本会建立 WebSocket 连接，保存电视签发的配对令牌，再发送三星遥控键值。第一次它发起连接，我只在电视上确认了一次，之后 Codex 就能从电脑端执行 Home、方向键、返回等常用操作。

这一步的意义不只是“用电脑当遥控器”。从此以后，Codex 可以一边操作电视，一边读取电视状态和网络日志，把原来需要我反复描述的排障过程变成可验证的数据链路。

出于安全考虑，我没有把配对令牌、设备 MAC 地址和完整局域网地址写进文章。它们没有复用价值，也不应该公开。

## 第二步：把 Mac 变成电视的香港出口

改地区和访问海外流媒体其实是两个问题：

1. Smart Hub 属于哪个地区，决定应用商店里能安装什么；
2. 电视访问互联网时从哪里出去，决定应用和视频服务能否正常连接。

只改 Smart Hub 不改网络，YouTube 仍然无法访问；只有代理没有改区，应用商店里又找不到 YouTube。因此两件事必须同时完成。

我的 Mac 使用 Clash Verge Rev，底层是 Mihomo。Codex 先确认软件当前配置和系统路由，再让我开启 TUN 模式。由于电视不能直接运行代理客户端，方案是让 Mac 充当电视的网关：

```text
三星电视（有线）
        │
        │ 默认网关指向 Mac
        ▼
Mac（Wi-Fi + Mihomo TUN）
        │
        │ 香港代理节点
        ▼
     互联网
```

我在电视的手动网络设置里保留原网段地址，把默认网关改为 Mac 的局域网地址，DNS 设置为 `8.8.8.8`。Codex 在 Mac 上开启 IPv4 转发，并通过 TUN 接管和分流电视流量。电视菜单里没有找到关闭 IPv6 的“专家设置”，但这没有阻断方案，Codex 根据实际连接记录继续验证，而不是停留在菜单名称上猜测。

电视重新联网后，Codex 从代理连接记录里确认：来源于电视的请求进入了 `DEFAULT-TUN`，海外连接经香港节点发出。也就是说，电视虽然插着路由器网线，实际出口已经由无线联网的 Mac 接管。

这里有个容易踩的坑：如果 Mac 的局域网 IP 由 DHCP 自动变化，电视保存的网关就会失效。我后来在路由器里为 Mac 做了 DHCP 地址保留，让它每次都拿到同一个局域网地址。

## 第三步：两个错误码，让“软切区”走到了尽头

网络通了以后，我先尝试风险更低的 Smart Hub 服务条款切区。按照常见方法，在服务条款页面打开地区列表并选中香港。但电视先后出现了两个错误。

![选择香港后，服务条款页面提示服务器正在维护](posts/images/samsung-codex-terms-error.jpg)

第一个是：

```text
服务器正在维护，请稍后重试。（7-3）
```

Codex 没有把它当成真的“服务器维护”。它对照代理日志发现，三星的 `.cn` 条款域名被现有规则判成了直连，而电视正在尝试完成跨区初始化。于是它调整路由，让相关请求经香港出口，再让我重试。

错误随之发生变化，页面下载等待约两分钟后提示：

```text
服务器正在维护中，请稍后重试。（0）
```

第二次，Codex 又检查了 DNS、Fake-IP 和真实 IP 解析，并把代理临时切到全局香港。连接确实已经从香港发出，但中国区 CDN 返回了异常的小响应，行为接近 403。我们继续尝试了分阶段路由：打开页面时保持可访问中国区服务器，提交地区时再切香港；结果依然是 `(0)`。

这时 Codex 做了一个很重要的判断：停止重复试错。

`7-3` 主要暴露了路由规则问题，`(0)` 则说明这台国行固件的服务条款流程还有服务端或固件侧限制。继续更换 DNS 和节点只是在同一层兜圈子，并不会改变电视内部保存的地区参数。因此，我们从低风险的“软切区”转向工程菜单，但同时提高了风险控制等级。

## 第四步：进入工程菜单前，Codex 先划定红线

我参考了[这篇三星电视改区记录](https://www.j000e.com/Tricks/modify_SamsungTV_region.html)。Codex 阅读后没有直接让我照着按，而是结合我的具体型号逐项核对，并确定普通遥控器无法进入需要的扩展工程菜单。

我准备了一部带红外发射功能的安卓手机。Codex 帮我找到并校验了 `IR Service Remote v1.2`：

```text
包名：com.wolf.servicercsam
SHA-256：fc45b7d8cd44e571a63d0f58c15472cbd615f7b479e0c0400b777de55eafbb3b
```

校验值的作用不是证明软件绝对安全，而是确保我安装的文件与这次核对的版本一致。在电视正常亮屏时，我用红外手机依次发送 `S1 → S2`，电视进入了扩展工程菜单。

![通过安卓手机红外遥控进入三星电视工程菜单](posts/images/samsung-codex-service-menu.jpg)

工程菜单的可怕之处在于，很多项目点一下就会写入，未必再弹确认框。Codex 让我先拍下 `Option`、`MRT Option`、`Production Option` 和 `Engineer Option` 的完整原始状态，再根据照片识别字段，明确只允许改三个值。

它同时给出了一份禁止触碰清单：

- 不进入 `Factory Reset`；
- 不修改 `Type` 和任何 Panel/面板参数；
- 不修改 ADC/WB、Calibration、Tuner；
- 不因为名称相似就尝试其他 Region 字段；
- 每改一项都拍照确认，不连续盲按。

这部分非常能体现 Codex 和普通教程的区别。教程给出的是一条通用路径，Codex 则根据我眼前这台电视的照片做判断，告诉我哪一项是目标、哪一项碰了可能直接造成硬件配置错误。

## 第五步：把 CHI_DTV 改成 HKG_DTV

电视原始的三个地区参数是：

| 项目 | 原值 | 目标值 |
|---|---|---|
| `Local Set` | `CHI_DTV` | `HKG_DTV` |
| `Language Set` | `CHINA` | `CHINA`（保持不变） |
| `Region` | `CHI` | `asia_dtv` |

![改区前，Local Set 的原值为 CHI_DTV](posts/images/samsung-codex-local-set-chi.jpg)

我按照 Codex 确认过的范围完成修改，然后正常退出并重启电视。注意，`Language Set = CHINA` 在香港区目标组合中仍然保持不变，并不是看到 `CHINA` 就全部改掉。

电视重启和 Smart Hub 初始化后，Codex 通过设备接口再次读取状态，确认 `countryCode` 已从 `CN` 变成 `HK`。这比“商店里看起来多了几个应用”更可靠：电视内部地区状态确实已经改变，而不只是网络出口换了位置。

随后，香港区应用商店里出现了：

- Netflix、YouTube、Disney+、Prime Video；
- Spotify、Viu；
- Apple TV、Apple Music。

到这里，地区和网络两个条件终于同时成立。

## 第六步：Codex 用真实视频流量验收

我打开 YouTube 播放视频，Codex 在 Mac 上观察来自电视的实时连接。视频分片持续请求 `googlevideo.com`，全部经香港线路传输，而不是只验证了应用首页能打开。

一次 39 秒的观察窗口里，电视下载了约 `36.4 MB`，平均速率约 `7.5 Mbps`，峰值约 `23 Mbps`。这个水平播放 1080p 很稳定，4K 也能用，但高码率片源的余量不算特别宽裕。Netflix 随后也能进入和播放。

这次验收让我意识到，“能打开应用”和“能顺畅播放”完全不是一回事。Codex 没有看到图标就宣布成功，而是继续追踪域名、出口和吞吐量，直到视频分片稳定传输。

## Apple TV 后记：电视地区对了，账号地区仍然不对

Apple TV 是最后一个插曲。最初它多次无法进入，我在应用商店里也没看到明显的重装按钮。删除应用并重新安装后，Apple TV 可以打开，却提示地区不受支持。

![Apple TV 可以打开，但账号地区仍提示不受支持](posts/images/samsung-codex-apple-region-error.jpg)

我们重新核对了所有电视侧信息：

- `Local Set = HKG_DTV`；
- `Language Set = CHINA`；
- `Region = asia_dtv`；
- 设备接口返回 `countryCode = HK`；
- Apple 相关流量可以走香港出口。

最后我才想起来，初始设置时登录的是中国大陆 Apple ID。也就是说，这次提示不是电视改区失败，而是账号商店地区仍在中国大陆。后续需要换用香港区 Apple ID，再单独完成 Apple TV 的账号验证。没有必要重新进入工程菜单，也不应该为了一个账号问题重复改电视参数。

## 这次到底是谁在操作

回头看，这不是“我问 AI 一个教程，然后自己折腾”的过程。更接近于 Codex 担任远程工程师，我负责它无法跨越的物理边界。

| Codex 完成的工作 | 我完成的工作 |
|---|---|
| 扫描局域网并识别电视控制端口 | 保持电视开机并确认配对 |
| 编写并运行 WebSocket 遥控脚本 | 使用实体遥控器处理初始设置 |
| 设计 Mac 网关、TUN 和 DNS 路径 | 在电视上录入网络参数 |
| 分析 `7-3`、`(0)` 对应的连接记录 | 告知屏幕错误并按要求重试 |
| 阅读参考博客并为具体型号做风险判断 | 用红外手机发送 `S1 → S2` |
| 读取工程菜单照片、核对原值和目标值 | 只修改获准的三个地区字段 |
| 通过设备状态确认 `countryCode = HK` | 打开应用并播放测试视频 |
| 监控视频域名、香港出口和实时速率 | 观察电视画面是否正常 |

Codex 最有价值的地方，不是替我按了多少次方向键，而是它把一个横跨电视固件、局域网、代理、DNS、账号地区和工程菜单的模糊问题，拆成了可以逐层验证的状态。每次失败后，它都能用新的证据缩小范围；遇到工程菜单这种高风险环节，又会主动把可操作范围收窄。

## 最后的复盘

这次改造有几个结论值得记住：

1. **改区和代理是两件事。** 港区商店解决应用供给，香港网络出口解决连接能力，缺一不可。
2. **有线电视和 Wi-Fi Mac 可以协作。** 只要在同一局域网，Mac 可以作为电视的固定网关，但需要为 Mac 保留稳定的局域网 IP。
3. **错误码只是起点，连接记录才是证据。** `7-3` 和 `(0)` 表面都写着服务器维护，背后的网络行为却不同。
4. **工程菜单应当是最后方案。** 先保存全部原值，只改经过型号和照片确认的字段，绝不顺手清理或重置。
5. **电视地区、网络地区、账号地区必须分开判断。** Apple TV 的问题最终属于 Apple ID，而不是三星电视地区。

以前遇到这种问题，我可能要在十几篇年代不同、型号不同的帖子之间反复比对，还不知道哪一步真正生效。这次 Codex 不仅给出操作建议，还直接接入局域网设备、编写工具、读取现场照片、分析实时流量，并在风险上升时调整策略。

我只负责给 AI 一双现实世界里的手，而它负责看清整个系统。
